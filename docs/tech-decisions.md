## Database connections

Two variables, both read from the environment only and never printed or logged:

- `DATABASE_URL`: the pooled string (PgBouncer, transaction mode). For app runtime in later phases.
- `DATABASE_URL_UNPOOLED`: the direct string. Used by `drizzle-kit migrate` and the content import script.

Reason: Neon's connection-pooling documentation lists schema migrations as a direct-connection use case, and transaction-mode pooling does not support session-level features. Both names are in `.env.example` with no values.

## Other choices

- `scripts/check-legend.mjs` is plain Node with no dependencies, so the content hook works before any install.
- Neon Auth variable names in `.env.example` are confirmed by the owner: `NEON_AUTH_BASE_URL` and `NEON_AUTH_JWKS_URL` come from the Neon console; `NEON_AUTH_COOKIE_SECRET` is generated by the owner. Their roles after Phase 2 are under "Phase 2 decisions".
- Neon MCP server: name `Neon`, type `http`, url `https://mcp.neon.tech/mcp`, authenticated by the owner, kept as is in `.kiro/settings/mcp.json`.
- The Vitest docs site timed out during setup (two attempts). The config uses only long-stable options (`defineConfig` from `vitest/config`, `test.include`) and was verified by running it.

## Phase 2 decisions

- **Decision 27 changed (owner, Phase 2): "Google or email and password, both through Neon Auth."** The original wording was "Google or username and password". Neon's managed auth (Better Auth) has no username sign-in: its supported methods are email and password and social providers, and Neon manages the plugin list, which has no username plugin (Neon docs: roadmap, plugins, authentication flow). A second auth system was ruled out. The visitor picks a **display name** at sign-up and it is shown in the game; the judge test account signs in with an email.
- **True version computed on the server (owner, Phase 2).** When a run starts the server issues the seed, loads the legend from Neon, runs the skeleton generator and stores the seed and the true version id. The client reports neither.
- **Auth goes through our own route under `/game`** so the session cookie is first-party and route loaders can read the verified session on server-rendered requests. Neon's session cookie otherwise belongs to Neon's auth domain, and Neon documents a server SDK for Next.js only.
- **`@neon/auth` is pinned exactly at 0.8.2.** We use its `@neon/auth/server` toolkit (framework-neutral, marked beta; Neon says to pin narrowly) and wrote a small TanStack Start adapter on it (`apps/game/src/server/auth.ts`) instead of a proxy of our own. Upgrade only on purpose, and re-run the smoke check after.
- **The proxy forwards five endpoints only:** `get-session`, `sign-in/email`, `sign-up/email`, `sign-in/social`, `sign-out` (`apps/game/src/server/proxyPath.ts`). Everything else, such as admin, organization, account deletion and profile update, gets 404.
- **Environment variables (game app):**
  - `NEON_AUTH_BASE_URL`: where the toolkit sends auth requests. The toolkit also derives the JWKS address from it.
  - `NEON_AUTH_COOKIE_SECRET`: at least 32 characters. It signs the session cache cookie that `getSession()` trusts, so whoever has it can forge a session. Rotating it makes every cached session check with Neon again.
  - `NEON_AUTH_JWKS_URL`: not read by any code in Phase 2 (the toolkit does not read it). Kept in `.env.example` for a later cross-domain JWT check.
  - `GUEST_WORLD` (default `banshee`) and `FEATURE_ARABIC` (`true` or `false`, default off). Checked on the first request a server process handles; an error names the variable and never its value.
  - Start's env plugin reads `.env` from the app folder only, so a small Vite plugin in `apps/game/vite.config.ts` loads the repo-root `.env` into the server's `process.env` (real environment variables win). `envPrefix: 'KIROWEEN_PUBLIC_'` means no variable from `.env` can reach the browser bundle.
- **CSRF:** once `src/start.ts` exists, Start no longer adds its default CSRF middleware, so `start.ts` lists `createCsrfMiddleware` itself. It covers server functions and POSTs to the auth proxy.
- **Display name:** 2 to 30 letters or digits of any script, with single spaces and `' . - _` between them. It is checked in the proxy on `sign-up/email` (`skeleton/src/account/displayName.ts`), because sign-up goes to Neon directly. An `image` field is dropped.
- **Error text colour:** `--color-danger-ink: #e06b6b` (6.04:1 on the background). The hub danger red `#b23a3a` is 3.31:1, below WCAG AA for text. The palette token is unchanged and no text uses it.
- **Known limit: run counts are client-reported.** Slots solved, Hint 2 uses, wrong answers and highest fear come from the client, within fixed limits (0–50 Hint 2 uses, 0–500 wrong answers, 0–100 fear; `won` needs every slot solved). The seed, true version and score are made on the server. A player can still report a better run than they played; the fix is server-side play state in the game phase.
- **Score:** 100 per slot solved, +50 for a won run (curse broken), −15 per Hint 2 use, −10 per wrong answer, never below 0 (`skeleton/src/score/score.ts`).

## Game app under `/game` (Phase 2, Task 2 spike)

The documented route worked; the `src/routes/game/` fallback was not needed. Config in `apps/game/vite.config.ts`:

- Vite `base: '/game/'`: assets and the server-function base (`/game/_serverFn/`).
- `tanstackStart({ router: { basepath: '/game' } })`: **needed**. With `base` alone, server routes worked but every page returned 404.

Proved in dev (`vite dev`) and in the production build (`vite build`, served by `apps/game/scripts/serve-build.mjs`):

| Check | Dev | Build |
|---|---|---|
| page `GET /game/` (SSR, loader ran a server function) | 200 | 200 |
| server route `GET /game/api/ping` | 200 | 200 |
| server function `/game/_serverFn/<id>`, same-origin | 200 | 200 |
| same server function, cross-site `Origin` | 403 (Start's built-in CSRF check) | 403 |
| `GET /`, `/_serverFn/<id>` outside the base | 302/404 | 307 redirect into `/game/...` |

Outside `/game` the app never serves content; it only redirects into `/game`. On the shared domain the atlas will own `/`, so those paths never reach this app.

The build output is `apps/game/dist/` (a fetch handler `{ fetch }` in `dist/server/server.js` plus `dist/client/`). `serve-build.mjs` is for local checks only; the Vercel setup is a later phase and `vercel.json` is unchanged.

Start's server functions come with a CSRF check (`Sec-Fetch-Site`, `Origin`, `Referer`). A plain `curl` call with none of these is refused, so smoke scripts send the same-origin headers a browser sends.

Pins added for the game app (exact): `@tanstack/react-start` 1.169.5, `@tanstack/react-router` 1.170.46 (the version Start depends on), `@neon/auth` **0.8.2** (its server toolkit is beta; Neon says to pin narrowly), `react` / `react-dom` 19.3.1, `@vitejs/plugin-react` 6.3.0, `tailwindcss` / `@tailwindcss/vite` 4.3.5, `@types/react` / `@types/react-dom` 19.3.0. Peer warning at install: `@better-auth/core` 1.7.26 wants `@better-fetch/fetch` 1.3.3 while `@neon/auth` pins 1.3.2; this is inside Neon's own dependency tree and is left as Neon ships it.

### `runs` has no foreign keys (owner approved, Phase 2)

`runs.legend_id` and `runs.true_version_id` are plain text, not foreign keys. The importer replaces a legend by delete then insert; a foreign key would cascade-delete every player's runs on each `db:import`, or block the import. The server checks the legend id against the catalogue, and the true version comes from the generator. `runs.user_id` has no foreign key into `neon_auth` either, because that schema belongs to Neon's managed auth.
