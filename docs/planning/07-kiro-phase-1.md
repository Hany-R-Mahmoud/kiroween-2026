# Kiro Phase 1: skeleton core

Written from `docs/phase-0-handover.md` (2026-11-19). Part A is what you do yourself. Part B is the prompt you paste into a new Kiro **Spec** chat. Phase 2 (auth and progress) is written only after Phase 1 is handed back and checked.

## Part A: before the prompt (you)

1. In Neon, open your project and copy the **pooled** connection string. Create a file named `.env` in the repo root (copy `.env.example`) and paste it after `DATABASE_URL=`. Do this in the editor yourself. Never paste it into any chat. `.env` is already gitignored.
2. Check `git status`: `.env` must not appear in the list.
3. In Kiro, start a new chat and choose **Spec** (not Vibe). Keep **Supervised** mode on.

## Part B: paste into a new Kiro Spec chat

```text
This is Phase 1 of our Kiroween 2026 entry: the skeleton core. Read docs/phase-0-handover.md, docs/tech-decisions.md, docs/planning/01-decisions.md and content/legend-format.md first. Steering files already apply.

Before the spec, do these small fixes and show me the diff:
a. Delete the stray folder .kiro/steering/.kiro/ (an accidental copy of mcp.json).
b. Keep the current .kiro/settings/mcp.json (server "Neon", type "http"); it is the working, authenticated config.
c. In LICENSE, replace <COPYRIGHT HOLDER> with the name from `git config user.name`.
d. Decisions taken on Phase 0 open items: stay on pnpm 9.15.9. The Neon Auth variable names in .env.example are confirmed (NEON_AUTH_BASE_URL, NEON_AUTH_JWKS_URL from the Neon console; NEON_AUTH_COOKIE_SECRET generated by me). Record both in docs/tech-decisions.md.

Then create a spec named "skeleton-core" for the package in skeleton/. Go through requirements, then design, then tasks, and wait for my approval after each. Scope is logic and data only, no UI:

1. Toolchain. Install TanStack Start-compatible versions of TypeScript, Vitest and fast-check in the workspace. Check which TypeScript major TanStack Start, Vite and Vitest officially support today; if TypeScript 7 is not supported by all three, pin the latest supported major instead. Record every pin and the reason in docs/tech-decisions.md. TypeScript strict mode.

2. Content model and parser. Typed model for a legend: meta, cold open, chapters (id, anchor, title, text), versions, documented/told table, fact pool, lead chains, game world (scenes, hotspots with swappable flag, spirit encounter, puzzle slots, curse-breaking puzzle, fear events, hints), theme pack tokens, asset list, sources. A parser reads content/legends/*.md into that model with runtime validation. It must accept both "### Hotspots" and "**Hotspots**" headings, and the ID formats described in legend-format.md, and prefix every ID with the legend id (banshee:f07). The parser never changes content files.

3. Database. Neon Postgres schema for the content model, stored with migration files in the repo (Drizzle ORM and drizzle-kit unless you find a concrete reason not to; record the choice). Use the Neon MCP server to create a development branch and apply migrations there. An import script loads all twelve legends from the parser into the database and is safe to run twice (no duplicates). Read DATABASE_URL from .env only. Never print, log or write a connection string anywhere else, and never put credentials in the repo or the chat.

4. Seeded randomness. A small deterministic RNG from a seed string. Same seed and same content always give the same run.

5. Run generator. Given a legend and a seed, produce a run: the true version, the true lead chain and the dead-end chains, the filled puzzle slots (each with its fact, the correct answer and exactly three wrong answers picked by the seed), hotspot roles after swaps, and both hints for every slot. Rules:
   - A slot only takes facts whose puzzle_types include the slot type.
   - Version-specific facts must match the true version; "all" facts always qualify.
   - [R] facts never fill a true-or-told slot.
   - The seed only picks a true version that has a lead chain which can be true for it. A lead marked "can be true when: never" is never the true lead.
   - Every dead end names a contradiction fact whose anchor exists.
   - Every puzzle slot and every step of the true lead has at least one meaningful hotspot; at least 5 decoys remain after swaps.
   - Hint 2 always deep-links to a chapter anchor that exists.
   - For answers that should appear in the story (all puzzle types except true-or-told and ritual-order), check that the answer text appears in the linked chapter after simple normalisation. Facts that fail this check are left out of generation and listed in docs/content-gaps.md with legend, fact id and reason. Do not edit the legend files to fix them.

6. Property-based tests with fast-check, run against all twelve parsed legends with random seeds: determinism; every slot filled; exactly one correct option and four distinct options; correct answer never among the wrong ones; the rules in step 5 hold for every seed; generation never throws for any seed. Also plain unit tests for the parser on two legends.

7. Hook. Add a Kiro agent hook that runs the skeleton test suite when a file under skeleton/src/ is saved and reports failures. It does not edit code.

8. Kiro usage log. Create docs/kiro-usage.md and add a short entry for Phase 0 and Phase 1: which Kiro features were used (spec, steering, hooks, MCP, property tests) and what each did. Keep it factual; it feeds the final write-up.

When all tasks are done, write docs/phase-1-handover.md with: files and folders created; versions pinned and why; the schema (tables and key columns); the Neon branch name; import result (rows per table); test results (number of properties, runs per property, pass or fail); the content-gaps summary; anything that needs my action. Do not commit or push. Stop and wait. Do not start Phase 2.
```

## Handover check (you, after Kiro finishes)

Phase 1 is done only when all of these are true:

- [ ] `.kiro/steering/.kiro/` is gone, and `LICENSE` shows your name.
- [ ] `.kiro/specs/skeleton-core/` has requirements, design and tasks files.
- [ ] `pnpm -r test` passes in the terminal (run it yourself once).
- [ ] The Neon console shows the development branch with the content tables filled.
- [ ] `docs/content-gaps.md` exists (it may list a few facts; that is expected).
- [ ] The new test hook exists in `.kiro/hooks/`.
- [ ] `docs/kiro-usage.md` exists.
- [ ] `git status` does not show `.env`, and no committed file contains a connection string.
- [ ] `docs/phase-1-handover.md` exists.

When the boxes are ticked, commit, push, and bring the handover file back here. The Phase 2 prompt (auth and progress) is written from it.
