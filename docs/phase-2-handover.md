## How auth is set up

- **Providers:** Google (Neon's shared credentials, development only) and email and password (sign-up open, no email verification). Neon Auth has no username sign-in, so decision 27 is now "Google or email and password". Organization, magic link and phone number plugins are off.
- **Neon side (`dev-skeleton-core`):** Better Auth provisioned through the MCP; trusted origin `http://localhost:3000`.
- **Our own route under `/game`:** `src/routes/api.auth.$.ts` forwards to Neon Auth through `@neon/auth/server`, so the session cookie is first-party. It forwards five endpoints only: `get-session`, `sign-in/email`, `sign-up/email`, `sign-in/social`, `sign-out`. Anything else gets 404, and methods other than GET and POST get 405. On `sign-up/email` it checks the display name (`cleanDisplayName`) and drops `image`.
- **Where sessions are checked:**
  - `src/server/auth.ts` `getVisitor()` calls the toolkit's `getSession()` on the server, from the request's cookies only. Any failure counts as a guest.
  - `src/server/middleware.ts`: `authMiddleware` puts the visitor on every server function's context. `requireUser` refuses a guest with 401 before the handler runs. It guards `startRunFn`, `finishRunFn`, `listMyRunsFn` and `myCompletedWorldsFn`, and the run service checks again.
  - `src/start.ts`: the CSRF middleware (listed explicitly, because Start drops its default once `start.ts` exists) covers server functions and POSTs to the proxy. A page-request middleware finishes the Google return trip and refreshes the session cache cookie.
  - No server function takes a user id from the client.
- **Variables:** `NEON_AUTH_BASE_URL`, `NEON_AUTH_COOKIE_SECRET` (at least 32 characters), `GUEST_WORLD`, `FEATURE_ARABIC`, `DATABASE_URL`. `NEON_AUTH_JWKS_URL` is read by nothing; the toolkit builds the JWKS address from the base URL. Names only in `.env.example`.

## The `runs` table

Migration `skeleton/drizzle/0001_runs.sql` (drizzle name `0001_runs`), applied to `dev-skeleton-core`; 2 migrations recorded.

- Enum `run_status`: `in_progress`, `won`, `restarted`, `abandoned`.
- Table `runs`: `id` uuid, `user_id`, `legend_id`, `seed`, `true_version_id`, `status`, `slots_solved`, `hint2_uses`, `wrong_answers`, `highest_fear`, `score`, `started_at`, `finished_at`.
- CHECK `runs_counts_non_negative`; CHECK `runs_finished_when_closed` (`finished_at` is set exactly when the run is not in progress).
- Index `runs_user_idx`; partial unique index `runs_one_in_progress` on `(user_id, legend_id)` where `status = 'in_progress'`.
- No foreign keys (approved): the importer replaces legends by delete then insert.
- Also: column `legends.model jsonb`, the parsed legend snapshot the server loads (12 of 12 filled; `db:check-models` says all 12 match).
- Starting a run closes the old in-progress run of that world as `abandoned` in the same transaction. A race on the unique index returns a fixed 409. The server makes the seed and the true version.

## The access rule

`skeleton/src/access/canEnter.ts`. A guest may enter the tutorial and the world in `GUEST_WORLD` (default `banshee`; checked against the legends in the database when the server first loads them, and a wrong value stops every request with an error naming the variable). A signed-in user may enter every world. The rule is applied in `getHall` and `enterWorld`. A refused guest gets a redirect to sign-in with no world data. Guest progress stays in the browser and never reaches the server.

## The score rule

`skeleton/src/score/score.ts`, computed on the server only: 100 per slot solved, +50 for a won run, −15 per Hint 2 use, −10 per wrong answer, never below 0. A client-sent score is refused (strict schemas). The counts it uses are client-reported within limits: Hint 2 uses 0–50, wrong answers 0–500, fear 0–100, slots up to the legend's slot count, and `won` needs every slot.
