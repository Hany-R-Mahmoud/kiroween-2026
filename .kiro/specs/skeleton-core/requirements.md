# Requirements: skeleton-core

Scope: logic and data for the `skeleton/` package. No UI, no auth (Phase 2). Source documents: `docs/planning/01-decisions.md`, `content/legend-format.md`, `docs/phase-0-handover.md`, `docs/planning/07-kiro-phase-1.md`.

## Glossary

- **Parser**: reads one legend Markdown file into the typed Legend model.
- **Legend**: the typed model of one file in `content/legends/`.
- **Run**: the output of the Generator for one legend and one seed.
- **Generator**: pure function `(legend, seed) -> Run`.
- **Slot**: one puzzle slot in a legend's "Puzzles" list (id, puzzle_type, candidate fact ids).
- **Qualifying fact**: a fact that may fill a slot under R5.2 to R5.4.
- **Content gap**: a fact whose answer text is not found in its linked chapter where it should be (R5.10).
- **Namespaced ID**: an ID prefixed with the legend id, for example `banshee:f07`.
- **Deep-link target**: a valid anchor. For a legend `<id>` with versions `v-x`, the valid set is: every chapter anchor `<id>--ch-<n>`, the versions anchor `<id>--versions`, and every per-version anchor `<id>--versions--v-x` (`legend-format.md` section 3).

## R1. Toolchain

**User story:** As the developer, I want a typed, tested toolchain so that later phases build on pinned, compatible versions.

1. THE workspace SHALL provide TypeScript with `strict: true`, Vitest and fast-check for `skeleton/`.
2. WHEN choosing the TypeScript major version, THE developer SHALL check the officially supported range of TanStack Start, Vite and Vitest, and SHALL pin the newest major supported by all three.
3. THE file `docs/tech-decisions.md` SHALL list every pinned version and the reason for each.
4. THE command `pnpm -r test` SHALL run the skeleton test suite and exit non-zero on any failure.

## R2. Content model and parser

**User story:** As the developer, I want every legend loaded into one validated typed model so that the generator and database never read raw Markdown.

1. THE Legend model SHALL cover: meta, cold open, chapters (id, anchor, title, sources, text, hook), versions (table and paragraphs), documented/told table, fact pool, lead chains, game world (scenes, hotspots with a swappable flag, spirit encounter, puzzle slots, curse-breaking puzzle, fear events, hints), theme pack tokens, asset list and sources.
2. WHEN given a legend file, THE Parser SHALL return a Legend or a list of errors, each with file, section and line.
3. THE Parser SHALL accept both `### Hotspots` and `**Hotspots**` headings, and equivalent heading variants for the other game-world sub-sections found in the twelve files.
4. THE Parser SHALL accept the differing ID formats (`f-01`, `f01`, `h-01`, `hs-hearth`, `lead-1`) and SHALL prefix every fact, hotspot, lead, version, slot and scene ID with the legend id.
5. THE Parser SHALL validate with a runtime schema (not only TypeScript types) and SHALL reject unknown puzzle types, anchors that are not deep-link targets, and facts that reference unknown versions. The versions anchor and per-version anchors are valid deep-link targets for facts, contradictions and Hint 2; they are never errors and never content gaps.
6. THE Parser SHALL never write to any file under `content/`.
7. WHEN run on `content/legends/*.md`, THE Parser SHALL load all twelve legends without errors.
8. WHEN reading a lead's "can be true when" line, THE Parser SHALL first check for the word "never": a line containing "never" means the lead cannot be true, even if the line names a version id. Otherwise THE Parser SHALL read the `v-<id>` from the sentence and check that it exists in that legend's versions table, and SHALL fail the parse if it does not.

## R3. Database

**User story:** As the developer, I want content stored in Neon with versioned migrations so that apps read content from the server, not from files.

1. THE repo SHALL contain SQL migration files generated by Drizzle ORM and drizzle-kit, unless a concrete reason against is recorded in `docs/tech-decisions.md`.
2. THE schema SHALL store every Legend model element in R2.1 using namespaced IDs as keys.
3. THE Neon development branch SHALL be created through the Neon MCP server, and THE migrations SHALL be applied to that branch, never to the default branch.
4. THE import script SHALL load all twelve parsed legends and SHALL be idempotent: running it twice SHALL leave identical row counts.
5. THE import script SHALL replace a legend's rows inside one transaction, so a failed import leaves the previous content unchanged.
6. THE code SHALL read connection strings only from the environment (loaded from `.env`), and SHALL never print, log or write them, nor include them in error messages. `DATABASE_URL` is the pooled string for app runtime later. `DATABASE_URL_UNPOOLED` is the direct string, used by `drizzle-kit migrate` and the import script.
7. THE import script SHALL use parameterized queries only.
8. THE file `.env.example` SHALL list `DATABASE_URL_UNPOOLED` with no value, and `docs/tech-decisions.md` SHALL record the two-variable decision.
9. WHEN the `dev-skeleton-core` branch exists, THE developer SHALL stop and ask the owner to paste both connection strings into `.env` personally. No migration or import runs before that.

## R4. Seeded randomness

**User story:** As a player, I want the same seed to give the same run so that runs are reproducible and testable.

1. THE RNG SHALL be a deterministic generator created from a seed string.
2. WHEN created twice from the same seed, THE RNG SHALL produce identical sequences.
3. THE code in `skeleton/` SHALL NOT use `Math.random` or the current time for game logic.
4. THE RNG SHALL provide: integer in range, pick one, shuffle, and sample without replacement.

## R5. Run generator

**User story:** As the game, I want a solvable run for any seed so that the player can always win by reading the atlas.

1. WHEN given a Legend and a seed, THE Generator SHALL return a Run containing: true version, true lead chain, dead-end chains, filled slots, hotspot roles after swaps, and hints 1 and 2 for every slot.
2. THE Generator SHALL fill a slot only with a fact whose `puzzle_types` include the slot's puzzle type and that is listed as a candidate for the slot.
3. WHERE a fact is version-specific, THE Generator SHALL use it only if its version equals the true version; facts marked `all` always qualify.
4. THE Generator SHALL NOT use a `[R]` fact in a `true-or-told` slot.
5. THE Generator SHALL choose the true version only among versions that have at least one lead chain that can be true for it, and SHALL never choose a lead marked "can be true when: never" as the true lead.
6. EACH dead-end chain SHALL name a contradiction fact whose anchor exists in the legend.
7. EACH filled slot and EACH step of the true lead SHALL have at least one meaningful hotspot after swaps.
8. THE Generator SHALL swap hotspot roles in pairs only. A pair is two hotspots that are both marked swappable, are in the same scene, and currently have different roles (one meaningful, one decoy). The hotspot that becomes meaningful SHALL take over the link (fact or lead step) of the one it replaces. THE Generator SHALL skip a swap that would leave a filled slot or a true-lead step with no meaningful hotspot. The seed SHALL decide how many pairs to swap, from zero up to the number of valid pairs. Because swaps are pairwise, the decoy count never changes, and AT LEAST 5 hotspots SHALL be decoys after swaps.
9. EACH filled slot SHALL have exactly four distinct options: the correct answer plus exactly three wrong answers picked by the seed from the fact's wrong-answer list. The correct answer SHALL NOT appear among the wrong ones.
10. FOR every slot type except `true-or-told` and `ritual-order`, THE Generator SHALL exclude a fact whose answer is not written in its linked text, using this matcher (owner decision, replaces the exact-phrase match):
    1. Normalise as before (case, diacritics, punctuation, markdown marks, plural `s`), and strip a leading label `documented:`, `told:` or `proposed:` from the answer.
    2. Split the answer into parts on commas, " and " and parentheses.
    3. A part passes when all its content words appear as whole words inside ONE paragraph of the linked text. Ignored words: a, an, the, of, and, or, to, in, on, at, with, near, about. Paragraphs are separated by a blank line; words split across two paragraphs do not count.
    4. The answer passes when every part passes.
    5. For `who-said-it`, the answer passes when the person's surname (the last word of the name) appears in the linked text.
    6. Implementation note: the matcher also folds a trailing "-ed" on words over four letters to the stem ("dressed" matches "dress"), because banshee f12 ("white dress") is otherwise not found in "dressed in white". Everything else is whole-word. Excluded facts SHALL be listed in `docs/content-gaps.md` with legend, fact id and reason.
11. THE Generator SHALL NOT edit legend files to resolve content gaps.
12. Hint 2 for every slot SHALL deep-link to a deep-link target of the legend (chapter, versions or per-version anchor). WHERE Hint 2 names the bare versions anchor, THE Generator MAY refine it to the per-version anchor of the true version; this is a refinement, not a correction, and is not reported as a content gap.
13. WHEN a slot has no qualifying fact left, THE Generator SHALL fail with a typed error naming legend, slot and seed, and a test SHALL fail for that legend. It SHALL NOT return a partial run. Such a legend SHALL be reported in `docs/content-gaps.md` and in `docs/phase-1-handover.md`. THE work SHALL NOT edit legend files and SHALL NOT loosen any rule to make a legend pass; the owner fixes content outside this spec.
14. THE Generator SHALL be pure: same Legend and seed always give an identical Run.
15. THE "Breaking the curse" final puzzle SHALL be carried through the Run as text (description, Hint 1, Hint 2); generating its options belongs to the game spec. WHERE the final puzzle is also listed as a normal row in the Puzzles table (for example banshee `pz-5`), THE Generator SHALL fill it, and THE tests SHALL cover it, exactly like every other slot.

## R6. Tests

**User story:** As the developer, I want property tests so that no seed can produce an unsolvable run.

1. THE test suite SHALL run property tests with fast-check over all twelve parsed legends and random seeds.
2. THE properties SHALL cover: determinism; every slot filled; exactly one correct option and four distinct options; correct answer never among wrong ones; every rule in R5.2 to R5.12 for every seed; generation never throws.
3. THE suite SHALL include plain unit tests for the Parser on two legends.
4. EACH property SHALL run at least 100 seeds per legend.
5. THE suite SHALL not need a database connection or network access.

## R7. Test hook

**User story:** As the developer, I want tests run when I edit skeleton code so that regressions show up at once.

1. WHEN a file under `skeleton/src/` is saved, THE hook SHALL run the skeleton test suite and report failures.
2. THE hook SHALL NOT edit code.

## R8. Kiro usage log

1. THE file `docs/kiro-usage.md` SHALL have a factual entry for Phase 0 and Phase 1 listing each Kiro feature used (spec, steering, hooks, MCP, property tests) and what it did.
2. THE same file SHALL record which global skills were used and what each found: read-the-damn-docs, ponytail, agent-tester, agent-security, agent-guard, verify-and-stop. A skill that is unavailable SHALL be recorded as such.

## R10. Skills and quality gate

1. WHILE writing and executing tasks, THE developer SHALL use these skills: read-the-damn-docs before using Drizzle, drizzle-kit, pg, Neon, Vitest or fast-check APIs; ponytail to keep each module minimal; agent-tester on the property and unit tests; agent-security on the import script, env loading and database code; agent-guard after each group of tasks; verify-and-stop for the final check.
2. Skills SHALL NOT override this spec, the steering files or the owner's prompt. On conflict, THE spec wins and the owner is told.
3. THE developer SHALL NOT use agent-pilot, agent-superpowers or any skill that starts sub-agents or its own workflow.
4. THE last task SHALL be a guard pass and a final verification before the handover is written.

## R9. Handover

1. WHEN all tasks are done, THE file `docs/phase-1-handover.md` SHALL list: files and folders created; versions pinned and why; schema (tables, key columns); Neon branch name; import row counts per table; test results (properties, runs per property, pass or fail); content-gaps summary; items needing owner action.
2. THE work SHALL NOT be committed or pushed, and SHALL NOT start Phase 2.

## Out of scope

UI, auth, progress storage, scene explorer, theme rendering, audio, multiplayer, Arabic content.

## Decisions taken at approval

1. Hotspot swaps are pairwise, as in R5.8.
2. "Can be true when" is parsed as in R2.8. The two "never" lines that also name a version (v-lab, v-marquess) are therefore never true leads.
3. Content gaps never block the spec: they are reported, not fixed (R5.13).
